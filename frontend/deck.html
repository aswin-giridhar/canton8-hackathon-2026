Live mandate The pitch
folio 01 / 09 Cantor8 Canton Hackathon · London 2026 · Track D1

The ledger refuses. Not the app.

A spending mandate for an AI agent, enforced by Daml. The cap, the allow-list and the expiry live on the ledger — so a compromised agent cannot spend past them, and there is no policy check in our backend to route around.

folio 02 / 09 The problem, in the standard's own words

AP2 defends against a compromised agent by asking the agent to behave.

A prompt injected, or otherwise malicious Shopping Agent attempts to approve multiple valid Checkouts using the same open Mandate.

AP2 · Security & Privacy Considerations — naming the attacker

…agents should avoid signing multiple, overlapping closed Mandates for the same open Mandate.

AP2 · the mitigation — a rule addressed to that same agent

That is circular. If the component is compromised, the mitigation that depends on it is void. The spec also does not address concurrency, and does not address revocation at all.

folio 03 / 09 What we built

The mandate is a ledger invariant, not a signed promise.

  • Cap, allow-list, expiry enforced in Daml choice bodies
  • Consume-once is free — a consuming choice archives the contract, so replay is impossible without a nonce store
  • Instant revocation the agent cannot block or delay
  • Narrowing is unilateral — the owner can cut off one counterparty without destroying the mandate; widening needs both signatures
  • Audit trail written in the same transaction as the spend, naming which rule permitted it
assertMsg "counterparty is not on the allow-list"
  (t.receiver `elem` allowedCounterparties)

assertMsg "charge would exceed the cap"
  (spent + t.amount <= cap)

ensure cap > 0.0 && spent >= 0.0
    && spent <= cap
folio 04 / 09 The agent holds no key

It spends its owner's money without the owner signing.

A choice body carries the authority of the contract's signatories. The mandate is signed by owner and agent, so a charge controlled by the agent executes with the owner's authority. Proven by control, not assertion:

agent debits the owner's funds directlyRefused
agent debits them through the mandateSettled

Visibility held constant across both, so the only variable is the mandate. Mutation confirms the mechanism: remove the owner from the signatories and it fails with missing authorization from Alice.

Mutation testing found two rules were double-guarded: disabling the cap assertion changes nothing, because the template's ensure catches it too. So the honest answer to "show us the line that stops it" is the ensure — the guard that survives someone deleting the explicit check.

folio 07 / 09 Contention, where AP2 implementations fail

Two charges race one mandate. One settles, one aborts. Every time.

Both submissions charge 1.0 against a cap of 1.0, fired simultaneously behind a barrier — two successes would prove overspend. Verified from the ledger, not the responses: exactly one successor mandate, spent = 1.0, original consumed.

Published work adds a runtime verifier with time-bound nonces to get this. On Canton it is what a consuming choice already is.

folio 08 / 09 What is not real

Said before you ask.

  • LocalNet, not DevNet. A real Canton ledger with a real synchronizer and a real registry — but local. DevNet is verified end to end and unfunded.
  • No compromised LLM was demonstrated. Two Claude runs refused the injection, one even configured as an obedient auto-executor. Good result, not a security control — so the compromise is simulated at the tool-call layer instead.
  • The owner/agent trust boundary is in-process in the wallet demo. In production the disclosure service is an HTTP call.
  • Our own harness reported a false pass once. It printed "no money moved" while every call was failing on a lookup error, not on policy. Caught, guarded two ways, and both guards verified to fire.
folio 09 / 09 Where it lands

The authorization layer p402 says is missing.

Cantor8 settled the first private AI-agent payment on Canton in April, and wrote that there is still no interoperable way for an agent to prove what it's allowed to do. That is the mandate — and p402's Agent Capability Registry is described as a Daml template that does not exist yet.

We are not claiming a first. That belongs to Cantor8. We are claiming the layer above it: limits an agent cannot exceed even when it has been talked into trying.
